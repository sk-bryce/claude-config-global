# Spec-Anchored Architecture for This Config

The rationale, research, and operating model behind how this repository is organized.
`decisions/0001-adopt-spec-driven-config-architecture.md` is the terse decision record;
this file is the living explanation it links to. When the two disagree, the ADR records
what was decided and this file explains why and how.

## The problem this solves

The config targets two harnesses and is expected to grow to roughly 20-30 skills plus
subagents, hooks, and settings. Two forces make plain hand-maintenance insufficient:

1. Ongoing evolution: artifacts are created, audited, and improved continuously.
2. Regeneration cycles: when a new harness or model version lands (a few times a year),
   an artifact may need to be substantially rewritten to use new capabilities or idioms.

The hard requirement is that intent, behaviors, and desired outcomes are not lost when
an artifact is rewritten. A chat's reasoning is amnesiac and dies with the session, so
the intent must live in a versioned file that both humans and agents read at work time.

## Why spec-anchored (and not the alternatives)

Spec-Driven Development (SDD) is the matured 2026 answer to intent durability. Birgitta
Boeckeler's taxonomy names three rungs:

- spec-first: a spec is written to drive a task, then discarded.
- spec-anchored: the spec is kept and evolved as the maintained description of behavior;
  the artifact is also maintained.
- spec-as-source: the spec is the only thing a human edits; the artifact is a pure
  generated byproduct.

We sit on spec-anchored. The deciding factor is that our generator is a non-deterministic
LLM. The standard rule for committing generated output says to commit it (rather than
regenerate on demand) when generation is slow, depends on external services, or is
non-deterministic, and to never hand-edit it without updating the source. All of those
hold for LLM-generated skills, so the committed artifact must remain the record of what
is actually loaded. That rules out spec-as-source, which practitioners flag as an
anti-pattern that inherits "the downsides of both MDD and LLMs: inflexibility and
non-determinism."

Kent Beck's framing is the operating principle: "a specification should function as a
hypothesis, not a verdict... implementation doesn't invalidate a spec, implementation
completes it. The failure mode is not having specs, it is failing to update them when
implementation teaches you something new." Specs here are living hypotheses updated with
what each cycle teaches, not frozen contracts.

## The four layers

Mature SDD setups (GitHub Spec Kit's constitution, AWS Kiro's steering files) separate
persistent governing context from per-unit specs from generated output. Our files map
onto that cleanly, with an added immutable history layer:

| Layer | Purpose | In this repo |
| --- | --- | --- |
| Constitution / steering | Persistent, runtime-loaded governing principles and facts | `CLAUDE.md`, `reference/*.md` |
| Specs | Per-artifact intent; the source a regeneration reads | `specs/*.md` (per type) |
| Generated artifacts | The actual loaded artifacts; committed but regenerable | `skills/`, `agents/`, mechanical outputs |
| Decisions | Immutable, dated rationale and history | `decisions/NNNN-*.md` |

Rules that keep the layers from collapsing into each other (each maps to an observed
failure of the old `BOOTSTRAP.md`):

1. Specs never copy artifact content. Drift in the old model came from duplicated
   content; a spec that references and never duplicates cannot drift that way.
2. Specs contain no imperative "how to generate" procedure. That lives in the authoring
   skills and `reference/`. Procedure duplication is what bloated the old file.
3. Specs are consulted per-artifact during scoped regeneration, never executed wholesale.
4. The constitution references specs and artifacts; it does not restate them (Spec Kit
   enforces the same rule: "AGENTS.md references the constitution without duplicating
   governance rules").

## Two classes of artifact

The right treatment differs by how deterministically an artifact regenerates.

| Class | Examples | Generation | Treatment |
| --- | --- | --- | --- |
| Mechanical | `hooks.json` twin, `mcp.json` copy, synced reference copies (for example `skills/skill-author/references/skills.md`) | deterministic projection | `scripts/sync.sh`, generated or hand-written and reviewed before commit; safe to regenerate every time; drift-checkable |
| LLM-generated | skills, subagents, prose behaviors | spec to artifact via an authoring skill | spec and artifact both committed; regenerate via authoring skill; gate with evals |

The two classes differ by how deterministically the artifact regenerates. A mechanical
artifact comes from a deterministic subset filter or projection, so `scripts/sync.sh`
regenerates and drift-checks it byte-for-byte. An LLM-generated artifact comes from a
judgment-driven rewrite - dropping a section, restating content in different prose,
reflowing structure - so no mechanical filter produces it, and it gates with evals instead
of a byte-identical diff.

"Delete the directory and regenerate" is fully safe for the mechanical class and
available-but-eval-gated for the LLM class, because the LLM result is behaviorally
equivalent when evals pass, not byte-identical.

## The regeneration lifecycle

1. Trigger: a
   `${CLAUDE_CONFIG_DIR:-~/.claude}/skills/cursor-projection/references/harness-matrix.md`
   update (a new or changed harness fact) or an eval regression. Not a calendar date.
2. Scope: grep the artifact tree for the changed capability to find only the affected
   artifacts.
3. Regenerate: invoke the artifact type's authoring skill with that artifact's spec
   section plus the updated matrix row. Intent is unchanged, so only harness-specific
   mechanics should move.
4. Gate: run the artifact's evals on each target harness, comparing against the committed
   prior version (see Evals).
5. Review: `git diff` the prior committed artifact against the new one. Because intent did
   not change, an oversized diff is a meaningful red flag.
6. Record: update the spec if the cycle taught something new; add a decision record if the
   change is a cross-cutting choice; stamp the artifact's provenance header.

Model-behavior-driven rewrites (a new model reads the same prose differently, with no
harness-matrix change) use the same machinery, triggered by the authoring skill's audit
mode plus eval regressions rather than a matrix change.

## Evals: what makes non-deterministic regeneration safe

Prompt changes are invisible regressions; there is no reviewable diff because the artifact
is natural language and the output is probabilistic. The eval gate is therefore not
optional for the LLM class. The 2026 consensus pattern, adopted here:

- Prefer deterministic assertions (contains, regex, JSON-shape, cost and latency limits)
  over model-graded ones; use an LLM rubric only for qualitative checks, and pin the judge
  model and rubric text.
- Run a paired comparison against the pinned prior version, asserting per-case that the new
  artifact does not regress, rather than only checking absolute floors.
- Pin and record the harness and model version with every eval run.
- Gate with a pass-rate threshold that tolerates minor model noise but fails real
  regressions.

Tooling: start with the native skill-creator/skill-author eval framework (trigger-evals),
which is already present and needs no new dependency. Revisit an external CI harness such
as promptfoo if and when a cross-harness, cross-model CI matrix is wanted.

## Provenance and drift

- Provenance: each generated artifact carries a header naming its source spec, and the
  agent, model, and harness version it was generated against. This closes the "which spec
  produced which behavior" gap cheaply and matches current practice (OpenSpec requires
  PRs to name the agent and model used). For Markdown artifacts the header extends the
  existing created/updated HTML comment with `spec:`, `generated-by:`, `model:`, and
  `harness:` fields, for example:

  ```markdown
  <!--
  created: 2026-07-23
  updated: 2026-07-27
  spec: specs/skills.md (skill-author section)
  generated-by: <agent>
  model: <model-alias-or-id>
  harness: <harness and version>
  -->
  ```

  Artifacts that predate provenance tracking carry the `spec:` pointer plus a
  `provenance: predates provenance tracking; regenerate to populate ...` note until their
  next regeneration fills in the remaining fields.
- Drift: for the mechanical class, `scripts/sync.sh` can run in a warn mode that reports
  when a live file was not generated from its current source (the chezmoi and Flux
  warn-versus-enforce pattern). For the LLM class, drift between a prose spec and a prose
  artifact is not mechanically detectable; the eval gate and the scoped diff are the
  substitute.

## Metadata headers

Every hand-authored Markdown file carries a `created`/`updated` header; the delimiter is
chosen by the file's role, not by preference:

- Standalone Markdown read on demand (`reference/`, `specs/`, `decisions/`, `docs/`): YAML
  frontmatter (`---`), the Markdown-native default and what most of `reference/` already uses.
- `CLAUDE.md`: an HTML comment (`<!-- -->`). Claude Code strips block-level HTML comments from
  `CLAUDE.md` before injecting it into context, so the header costs no tokens there; a YAML
  `---` block is not stripped from that injection and would enter context as content (the docs
  strip frontmatter only for the auto-memory size check, not for injection). The stripping is
  specific to auto-injection: opening any of these files on demand with a file-reading tool
  still shows everything, which is why standalone reference/spec/decision files gain nothing
  from comments and use `---` by convention instead.
- Generated artifacts that already need YAML frontmatter for a parsed schema
  (`skills/*/SKILL.md`: `name`/`description`/`model`) keep `created`/`updated`/provenance in an
  HTML comment directly beneath that frontmatter, so provenance is never mistaken for schema.
- Non-Markdown files use their native comment syntax (`#` for `scripts/*.sh`); JSON has no
  comment mechanism and carries no header.

## Anti-patterns to avoid

- Big ball of specs: specs sprawling into an unnavigable, duplicative mass. Keep them
  lean, hypothesis-shaped, and per-type.
- Copied artifact content in a spec (the old drift source).
- Imperative generation procedures in a spec (belongs in authoring skills).
- A model writing a hook registration into a live location, or committing script or hook logic
  unreviewed (the policy is: generate freely, review before commit, and keep hook registration a
  human step; see `decisions/0003-hooks-and-scripts-authoring-policy.md`).
- Spec-as-source for LLM artifacts (non-determinism plus inflexibility).
