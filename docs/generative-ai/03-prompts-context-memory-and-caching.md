# Chapter 3: Prompts, Context, Memory, and Caching

## In short

- A prompt is everything sent to the model to elicit one response: a system/developer prompt (application-level instructions), a user turn, and prior assistant turns. Wording, structure, and examples change output quality because the model is predicting a continuation of exactly that text, nothing else.
- The context window is a hard token budget shared by the system prompt, conversation history, retrieved documents, and tool outputs. Exceeding it causes truncation, summarization, or an outright error, depending on the system. "Context engineering" is the discipline of deliberately curating what occupies that budget.
- Context and memory are different things: context is what is in the model's window for this call; memory is information persisted outside the window and deliberately reloaded later, often via summaries, retrieval, or explicit memory files.
- A session (or conversation, or thread) is one continuous exchange with an accumulating context window. What happens when a session ends, and what if anything carries into the next one, is a product design decision, not a property of the model itself.
- Prompt caching (Anthropic, OpenAI, and others) reuses the computed representation of a static prompt prefix across requests, cutting cost and latency. It is an exact-prefix-match optimization, distinct from semantic caching, which matches on meaning rather than identical text.
- See [Chapter 2](02-models-training-and-inference.md) for how tokens and inference actually work under the hood, [Chapter 4](04-agents-subagents-harnesses-and-tools.md) for how agents manage context and memory across tool calls and subagents, [Chapter 5](05-retrieval-embeddings-and-vector-databases.md) for retrieval and vector databases, and [Appendix C](appendices/appendix-c-costs-and-getting-value.md) for the cost arithmetic of caching strategies.

## 1. Prompts and prompt engineering

### 1.1 What a prompt is

A prompt is the complete input handed to a language model for a single generation step. In a raw completion API, that is literally just a string. In the chat-style APIs that dominate today's tooling (Anthropic's Messages API, OpenAI's Chat Completions and Responses APIs), the prompt is structured as an ordered list of messages, each tagged with a role:

| Role | Who writes it | Purpose |
| --- | --- | --- |
| System / developer | The application builder, not the end user | Standing instructions: persona, constraints, output format, available tools. Sits outside the visible conversation. |
| User | The end user (or the calling application on the user's behalf) | The actual request or turn in the conversation. |
| Assistant | The model | The model's own prior responses, replayed back to it as conversation history on the next turn. |
| Tool / tool result | The application, on behalf of a tool the model invoked | The output of a function or API call the model asked to run, fed back in so the model can use it. |

OpenAI's Model Spec documents this explicitly as a "chain of command": each instruction carries a level of authority depending on its source, from highest to lowest, non-overridable root-level rules built into the model, OpenAI-controlled system-level defaults, `developer`-role instructions from the application (what most people mean by "the system prompt"), and `user`-role instructions carrying the end user's own words; messages generated by the model itself carry the `assistant` role and have no inherent authority of their own. A lower-authority instruction is followed only when it does not conflict with anything higher in that chain (OpenAI, "Model Spec: Chain of command," see References).

Anthropic's Messages API uses a similar shape: a single top-level `system` parameter plus an alternating `user`/`assistant` `messages` array, with tool results injected as a special content block inside a `user` turn. The role names differ slightly by provider, but the underlying hierarchy, application instructions outrank end-user wording, which outranks nothing at all, is consistent across both.

The important mental model: nothing is "remembered" between calls. Each request to the API is stateless from the model's point of view. What looks like a continuous conversation is the calling application resending the entire message history (system prompt plus every prior turn) on every single request. This is exactly why the context window (Section 2) exists as a hard limit: the model's "memory" of the conversation so far is just more text in the prompt, competing for the same finite budget as everything else. [Chapter 2](02-models-training-and-inference.md) covers what the model does with that prompt internally, token by token, during inference.

A minimal, complete prompt, in the shape an API actually sends it, looks roughly like this:

```text
[system]    You are a concise technical writing assistant. Prefer short
            sentences. Never use marketing language.

[user]      Rewrite this sentence for clarity: "Our platform leverages
            best-in-class synergies to deliver value."

[assistant] "Our platform combines proven techniques to help you get
            results."

[user]      Now do the same for: "We utilize a robust methodology to
            actualize customer success."
```

Every field here is resent on every call. The `[assistant]` turn is not the model "remembering" what it said; it is the application replaying the model's own prior output back to it as plain input text, which both keeps the conversation coherent and lets the model condition its next answer on the style and content it already committed to.

### 1.2 Why wording, structure, and examples change output quality

A language model produces its next token by conditioning on every token that came before it ([Chapter 2](02-models-training-and-inference.md) covers the attention mechanism that makes this possible). This has three direct, practical consequences for prompt design:

- **Ambiguous wording gets resolved arbitrarily.** If a prompt admits two reasonable readings, the model picks one, and it may not be the one you intended. Precision in the prompt is not a nicety, it directly narrows the space of plausible continuations.
- **Structure narrows the model's guess about the task.** A prompt formatted as a clear list of requirements, with headers, delimiters, or numbered steps, gives the model a template to pattern-match against. A single dense paragraph makes it harder for the model to identify what's actually being asked, and easier for it to skip a requirement buried mid-sentence.
- **Examples ("shots") demonstrate the task instead of describing it.** Showing the model a couple of correct input-output pairs is often more reliable than explaining the rule behind them in prose, because the model is directly conditioning on a concrete pattern rather than inferring one from an abstract description.

These are not stylistic preferences; they follow from how next-token prediction works, and they are the basis for the concrete techniques below.

### 1.3 Core prompting techniques

**Zero-shot prompting** asks the model to perform a task with instructions only, no worked examples:

```text
Classify the sentiment of this review as positive, negative, or neutral.

Review: "The battery life is disappointing but the screen is gorgeous."
```

Modern instruction-tuned models handle a large range of common tasks well zero-shot, because instruction tuning specifically trains the model to follow a natural-language task description ([Chapter 2](02-models-training-and-inference.md) covers instruction tuning and RLHF).

**Few-shot prompting** adds one or more example input-output pairs before the real query, letting the model infer the task format from demonstration rather than description:

```text
Review: "Terrible battery, love the camera." -> mixed
Review: "Best phone I've owned." -> positive
Review: "The battery life is disappointing but the screen is gorgeous." -> ?
```

Few-shot prompting is not just a prompting trick; it names a documented capability of large language models. Brown et al.'s 2020 paper introducing GPT-3, "Language Models are Few-Shot Learners," showed that a sufficiently large model can perform a new task from only a handful of in-context examples, with no gradient update or fine-tuning, purely by conditioning on the demonstrations included in the prompt (Brown et al., 2020, see References). This capacity to learn a task pattern from examples given only in the prompt is usually called in-context learning.

**Chain-of-thought (CoT) prompting** asks the model to produce intermediate reasoning steps before its final answer, rather than jumping straight to a conclusion:

```text
Q: A store had 23 apples. They sold 15 and then received a delivery of 8 more.
How many apples do they have now?
A: Let's think step by step.
```

Wei et al.'s 2022 paper, "Chain-of-Thought Prompting Elicits Reasoning in Large Language Models," showed that including a few worked examples with explicit reasoning steps (rather than just a final answer) substantially improves performance on arithmetic, commonsense, and symbolic reasoning tasks, and that the benefit is an emergent property of model scale: it appears reliably only in models on the order of 100 billion parameters and larger (Wei et al., 2022, see References). Note this is distinct from a model's built-in "extended thinking" or "reasoning" mode (covered in [Chapter 2](02-models-training-and-inference.md)), where the model generates a reasoning trace as part of its own inference process regardless of prompt wording; chain-of-thought prompting is the older, purely prompt-driven version of the same idea, and still useful with models that do not have a dedicated reasoning mode, or where you want the reasoning to follow a specific shape.

**Role or persona framing** assigns the model an identity or frame of reference, typically in the system/developer prompt:

```text
You are a senior database administrator reviewing a colleague's migration
script for correctness and safety. Be direct about risks; do not soften
warnings for politeness.
```

This works by conditioning generation on a persona that has an implicit, learned association with certain vocabulary, priorities, and level of directness in the training data. It is a real and useful lever, but it is easy to overstate: a persona does not grant the model any capability it did not already have, and it does not substitute for giving it the specific facts, constraints, or examples the task actually requires.

**Structured output requests** ask the model to return output conforming to a specific format, most commonly JSON matching a schema, rather than free-flowing prose. Both major providers now support this natively rather than relying purely on prompt wording: Anthropic's structured outputs feature lets a request specify `output_config.format` with a JSON Schema, and the API guarantees the returned text is valid JSON conforming to it (Anthropic, "Structured outputs," see References). A minimal schema for extracting a support-ticket classification looks like this:

```json
{
  "output_config": {
    "format": {
      "type": "json_schema",
      "schema": {
        "type": "object",
        "properties": {
          "category": { "type": "string", "enum": ["billing", "shipping", "product"] },
          "urgent": { "type": "boolean" }
        },
        "required": ["category", "urgent"],
        "additionalProperties": false
      }
    }
  }
}
```

This is a case where an API-level constraint has substantially replaced what used to be pure prompt engineering (asking the model in prose to "respond only in valid JSON and nothing else," which older models would periodically violate by adding commentary or markdown fencing around the JSON). Constrained decoding at the API level, where the model is only permitted to generate tokens the schema allows, is far more reliable than requesting a format in words.

### 1.3.1 Combining techniques, and a quick comparison

These techniques are not mutually exclusive; a production prompt commonly stacks several of them at once, for example a role-framed system prompt, a few worked examples, an instruction to reason step by step, and a JSON schema for the final answer. As a quick reference:

| Technique | What it adds to the prompt | Best suited for |
| --- | --- | --- |
| Zero-shot | Instructions only | Common, well-understood tasks the model has likely seen described many times in training |
| Few-shot | Worked input-output examples | Tasks with an idiosyncratic or unusual format that is easier to show than describe |
| Chain-of-thought | An instruction (or examples) inducing step-by-step reasoning before the final answer | Multi-step arithmetic, logic, or planning tasks where jumping straight to an answer causes errors |
| Role/persona framing | An identity or frame of reference, usually in the system prompt | Steering tone, register, and implicit priorities; weaker for injecting facts or hard constraints |
| Structured output | A schema the response must conform to | Any output consumed by downstream code rather than read by a human |

### 1.4 Where prompt engineering has diminishing returns

Prompt engineering is cheap to iterate on and has no infrastructure cost, which makes it the right first lever to pull. But it has real limits:

- **It cannot supply facts the model does not have or cannot see.** No amount of clever wording gives the model access to your private documents, your live database, or events after its training cutoff. That is a retrieval problem, not a prompting problem; see [Chapter 5](05-retrieval-embeddings-and-vector-databases.md) for retrieval-augmented generation (RAG) and vector databases.
- **It cannot reliably change deep behavioral patterns at scale.** A system prompt can bias tone, format, and priorities, but it competes on every single request with everything the model learned during training and post-training. If you need a model to reliably behave a particular way across a very large number of edge cases, at a level a prompt cannot reach, that points toward fine-tuning. [Chapter 7](07-related-and-advanced-topics.md) covers the fine-tuning-versus-prompting trade-off in depth: prompting is faster, cheaper, and reversible, while fine-tuning is more expensive and rigid but can bake in behavior that a prompt cannot reliably force.
- **It does not scale to large amounts of task-relevant information.** Stuffing more and more instructions and reference material into a single prompt runs headlong into the context window limit (Section 2) and, before that, into the empirical fact that model performance on long inputs degrades well before the window is technically full (see "context rot" in Section 2.3).
- **It cannot reliably separate trusted instructions from untrusted data.** A model reads the system prompt, the conversation, retrieved documents, and tool output as one undifferentiated stream of tokens; wording a system prompt more forcefully does not give it a robust way to tell "an instruction from the application developer" apart from "text that happens to look like an instruction, embedded in a document the model was asked to summarize." This limitation, not any specific wording choice, is why untrusted content in context is a security concern; [Chapter 6](06-security-privacy-and-data.md) covers prompt injection and related risks in depth.

In short: prompt engineering is necessary and often sufficient for well-scoped tasks, but it is one tool among several, not a substitute for retrieval or fine-tuning when the task genuinely requires them.

## 2. Context and the context window

### 2.1 What "context" means

In an LLM conversation, "context" is all the text the model can actually see when generating its next response. Anthropic's documentation describes the context window as the model's "working memory": everything the model can reference when generating a response, as distinct from the (much larger, and now frozen) corpus of data it was trained on (Anthropic, "Context windows," see References). Context is assembled fresh, from scratch, on every single request; it is not something the model carries around between calls on its own.

Concretely, the context window for a given request is filled by, in typical order:

1. The system/developer prompt.
2. Tool definitions (the names, descriptions, and schemas of any tools the model can call).
3. The conversation history so far: every prior user and assistant turn.
4. Any documents, retrieved passages, or file contents inserted into the conversation.
5. The results of any tool calls the model has made.
6. The model's own output for the current turn, including any extended-thinking/reasoning tokens, which also count against the same budget.

### 2.2 The context window as a hard token budget

The context window is measured in tokens, not characters or words ([Chapter 2](02-models-training-and-inference.md) covers what a token actually is and how text is tokenized). It is a genuinely hard limit, shared across every category of content above; there is no separate quota for "system prompt" versus "conversation history" versus "documents." As of mid-2026, per Anthropic's documentation, a 1,000,000-token context window is now the norm for current flagship Claude models (Opus 5 and Sonnet 5 among them), while only older or smaller models in the lineup remain at 200,000 tokens (Anthropic, "Context windows," see References).

The window is a single shared pool, and every category of content competes for the same space. A hypothetical request against a 200,000-token window might break down like this:

```text
+-------------------------------------------------------+  200,000 tokens total
| System prompt                          ~2,000 tokens   |
| Tool definitions                       ~3,000 tokens   |
| Retrieved documents (RAG, [Chapter 5](05-retrieval-embeddings-and-vector-databases.md))  ~40,000 tokens   |
| Conversation history so far           ~90,000 tokens   |
| Most recent tool call results         ~15,000 tokens   |
| Remaining budget for this turn's      ~50,000 tokens   |
|   input + the model's output                           |
+-------------------------------------------------------+
```

Nothing in that diagram is fixed; a long retrieved document or a chatty multi-hour conversation history can dominate the budget just as easily as a large tool result can. This is precisely why context engineering (Section 2.3) treats every one of these categories as a lever to manage, not just the conversation history.

What happens when a request would exceed the window depends on the system:

- **Hard rejection.** Anthropic's API returns a 400 `invalid_request_error` ("prompt is too long") if the input alone already exceeds the model's context window before any output is generated (Anthropic, "Context windows," see References).
- **Truncation mid-generation.** On newer Claude models, if the input plus the requested output length together exceed the window, the request is accepted, but generation stops early with a `model_context_window_exceeded` stop reason if it hits the ceiling (Anthropic, "Context windows," see References).
- **Rolling truncation in chat UIs.** Consumer chat interfaces often manage the window differently from the raw API: Anthropic notes that an interface like claude.ai can manage the context window on a rolling, first-in-first-out basis, silently dropping the oldest turns to make room for new ones, rather than erroring out (Anthropic, "Context windows," see References).
- **Automatic summarization (compaction).** Rather than truncating or erroring, a system can automatically summarize older parts of the conversation before the limit is reached, freeing token budget while preserving the gist. Anthropic offers this as server-side "compaction," which condenses earlier conversation content into a summary once a configured token threshold is crossed, so the conversation can continue past what the raw window would otherwise allow (Anthropic, "Compaction," see References).

The practical implication is that a very large nominal context window is not the same thing as "the model won't need context management." Every one of these outcomes (a hard error, a silent drop of old information, or an automatic summary) is a meaningfully different user experience, and which one an application gets is a deliberate design and configuration choice, not an inherent property of "having a big context window."

### 2.3 Context rot, and context engineering as a discipline

More tokens in context is not automatically better. Anthropic's own documentation names this directly: "As token count grows, accuracy and recall degrade, a phenomenon known as context rot. This makes curating what's in context just as important as how much space is available" (Anthropic, "Context windows," see References). That single-paragraph framing is Anthropic's own summary of the effect; for the underlying research literature it draws on, including the specific benchmarks that measured it, where Claude has and has not been directly tested, and where the evidence is still thin, see [`docs/context-rot.md`](../context-rot.md).

This observation is the basis for context engineering: the deliberate discipline of curating what occupies the context window, as distinct from prompt engineering, which is about how you phrase the instructions themselves. Anthropic's engineering team frames the shift explicitly: "the challenge isn't just crafting the perfect prompt, it's thoughtfully curating what information enters the model's limited attention budget at each step," and states the guiding principle as finding "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome" (Anthropic, "Effective context engineering for AI agents," see References).

That same post outlines several concrete strategies, most of which matter more for long-running, multi-turn agents than for a single one-off prompt (and are covered in depth in [Chapter 4](04-agents-subagents-harnesses-and-tools.md), since they are primarily agent-harness concerns):

- **Compaction**: summarizing a conversation nearing its limit and continuing from the summary rather than the full history.
- **Structured note-taking (agentic memory)**: having the agent write notes to storage outside the context window, to be pulled back in later, rather than keeping everything active at once. This is the conceptual bridge to Section 3 below.
- **Tool-result clearing**: replacing old, bulky, re-fetchable tool outputs (file contents, API responses) with a short placeholder once they are no longer immediately needed, while keeping a record that the call happened.
- **Sub-agent isolation**: delegating a sub-task to an agent with its own fresh context window, and returning only a condensed summary to the parent, rather than accumulating everything in one shared window.

The underlying point generalizes beyond agents: whether you are hand-writing a single prompt or designing a multi-step system, treating the context window as a scarce, curated resource, rather than a bucket to fill with everything that might conceivably be relevant, produces measurably better output.

## 3. Memory

### 3.1 Context versus memory

Context and memory are frequently conflated, but the distinction matters:

| | Context | Memory |
| --- | --- | --- |
| Scope | What is in the model's window for this specific call | Information persisted outside the window and deliberately reloaded |
| Lifetime | Exists only for the duration of the request (and the session that assembled it) | Intended to survive across sessions, sometimes indefinitely |
| Mechanism | Assembled fresh on each API call from prompt, history, and retrieved content | Written to durable storage, then selectively pulled back into context later |

Put differently: memory is a mechanism for getting information into context in a later session that would not otherwise be there, because the conversation that originally produced it is over and its history is not being resent.

### 3.2 Short-term versus long-term memory

**Short-term (working) memory**, in this domain, generally just means the conversation history within the current session, living in the context window itself. It requires no special infrastructure: the application simply keeps resending prior turns. Its limit is the context window (Section 2) and the degradation ("context rot") that comes with filling it.

**Long-term (persistent) memory** means information deliberately saved outside any single session's context window and retrieved into a later session's context. This requires an explicit system: somewhere to write the information, a decision about what is worth keeping, and a mechanism to decide what to load back in and when.

### 3.3 How real products implement persistent memory

There is no single standard architecture; documented real-world implementations use several distinct patterns, often combined:

**Automatic conversation summarization.** Anthropic's consumer memory feature for Claude.ai works this way: Claude reads, writes, and updates a set of memory entries in real time as a conversation happens, rather than on a fixed schedule, and that accumulated memory is then used to provide context for new, otherwise-unrelated conversations. This real-time behavior replaced an earlier version of the same feature, which instead summarized conversations and synthesized key insights on a recurring daily cycle; that legacy behavior still applies to some Enterprise and Team accounts (Anthropic, "Use Claude's chat search and memory," see References).

OpenAI's ChatGPT has a comparable pair of mechanisms: explicit "saved memories," which are discrete facts the user asks it to remember or that it proactively records, and a separate "reference chat history" or "memory sources" capability that lets the model draw on the substance of past conversations more broadly, with periodic updates that keep what it has learned current and reduce stale or contradictory entries (OpenAI, "ChatGPT Release Notes," see References).

In both cases, the underlying pattern is the same: an asynchronous background process condenses raw conversation history into a smaller, denser artifact, and that artifact, not the raw history, is what actually gets loaded into a future session's context.

**Explicit, agent-managed memory files.** Rather than an automatic background summary, the model itself can be given a tool to read and write persistent notes as part of doing its job. Anthropic's memory tool is a concrete, documented example: when enabled, "Claude can create, read, update, and delete files that persist between sessions, building up knowledge over time without keeping everything in the context window," typically under a `/memories` path that the calling application maps onto real storage it controls (Anthropic, "Memory tool," see References).

This is structured note-taking as described in Section 2.3, viewed from the memory side rather than the context-management side: the same underlying pattern (write it out, load it back in later) serves both as a way to relieve context pressure within a long session and as a way to persist state across sessions entirely.

Anthropic has since extended this into a first-party service, memory stores, giving developers a managed, filesystem-like store that can be attached to an agent session at creation time specifically so state (user preferences, project conventions, prior mistakes) survives across sessions that otherwise start with a completely fresh context (Anthropic, "Memory," see References).

**Retrieval-based memory.** A third pattern stores past interactions (or facts extracted from them) as embeddings in a vector database, and retrieves the most relevant ones into context based on similarity to the current query, rather than replaying a fixed summary or a hand-maintained file.

This is architecturally the same retrieval mechanism used for RAG over external documents; the only difference is that the corpus being retrieved from is the system's own conversation history or extracted facts about the user, rather than a knowledge base of documents. [Chapter 5](05-retrieval-embeddings-and-vector-databases.md) covers vector databases and embedding-based retrieval in depth; the memory use case described here is one of the two primary applications of that infrastructure (RAG over documents being the other).

In practice, production systems often combine these: a lightweight retrieval or note-taking layer for facts, alongside periodic summarization to keep the aggregate compact. As a quick comparison of the three patterns:

| Pattern | What is stored | How it re-enters context | Documented example |
| --- | --- | --- | --- |
| Automatic summarization | A condensed synthesis of past conversations, regenerated periodically | Injected wholesale at the start of a new session | Claude.ai memory; ChatGPT's saved memories and reference chat history |
| Explicit memory files | Discrete notes or documents the agent itself writes and organizes | Read back in, often selectively, via a file or memory-tool call | Anthropic's memory tool and memory stores |
| Retrieval-based memory | Embeddings of past interactions or extracted facts in a vector store | Retrieved by similarity to the current query, on demand | Custom RAG-over-history architectures ([Chapter 5](05-retrieval-embeddings-and-vector-databases.md)) |

### 3.4 Memory and user control

Because persistent memory means information about a user or a task outlives any single conversation, every documented consumer implementation pairs it with explicit user controls: a way to view what has been stored, delete individual items, disable the feature entirely, and start a session that neither reads from nor writes to memory (Anthropic's and OpenAI's Temporary Chat, covered in Section 4). This is not incidental; it follows directly from memory being, definitionally, data retained about a person across time. [Chapter 6](06-security-privacy-and-data.md) covers the privacy and data-handling implications of that retention in depth.

## 4. Sessions

A **session** (also called a conversation or a thread, depending on the product) is one continuous exchange between a user (or calling application) and a model, over which a single, accumulating context window is maintained. Each new turn in the session resends the entire prior history alongside the new message, which is why, mechanically, a session is really just "a context window that keeps growing."

Whether anything survives when a session ends is entirely a product decision, not something inherent to the model:

- A raw API call has no concept of a session at all. The calling application decides what "a conversation" means, stores the message history itself, and resends whatever it wants on the next call. Nothing persists unless the application explicitly saves it somewhere.
- A consumer chat product (Claude.ai, ChatGPT) typically does treat each conversation as a bounded, named session, but layers a separate persistent-memory system on top, of the kind described in Section 3, specifically so that some information does survive into a brand-new session even though the full raw transcript of the old one is not resent.
- Some products offer an explicit escape hatch, a mode (Anthropic calls it Temporary Chat, and OpenAI's equivalent uses the same name) that suppresses both persistence into and retrieval from the memory system for that one session, useful when a user wants a conversation that leaves no lasting trace (Anthropic, "Use Claude's chat search and memory"; OpenAI, "ChatGPT Release Notes," see References).

This connects directly back to Section 2: a long session is, mechanically, nothing more than a context window that keeps accumulating turns until something intervenes, whether that is a hard limit, a rolling truncation, or an automatic compaction. "The session is getting long" and "the context window is filling up" are two descriptions of the same underlying fact, one from the user's perspective and one from the system's.

### 4.1 Sessions in agentic and developer tools

The same concept shows up under different names once you move from a chat UI to a developer-facing tool. An agent harness ([Chapter 4](04-agents-subagents-harnesses-and-tools.md)) typically exposes a session or conversation identifier that the application uses to fetch and resend the right message history on each turn; a coding agent running for several hours on one task is, from the model's perspective, one continuously growing context window.

That single fact, that a long-running agent session is mechanically indistinguishable from a very long chat conversation, is exactly why long-running agent harnesses lean so heavily on the compaction and memory-file strategies from Sections 2.3 and 3.3, rather than simply letting the window fill up and error out. Practically, the same architectural question, "what happens when this gets long," applies whether the session is a person chatting in a browser tab or an autonomous agent working through a multi-hour task with no human watching each turn.

## 5. Caching

### 5.1 Why re-processing the same prompt on every request is wasteful

Every API call to an LLM requires the model to process the entire prompt from the beginning, one token at a time, before it can generate a single output token; [Chapter 2](02-models-training-and-inference.md) covers this "prefill" phase of inference in detail. If your application sends a long, mostly unchanging system prompt, a large document, or an extensive tool-definition list on every single request, and only the last line or two actually changes between calls, the model is redoing the same expensive computation over and over for no benefit. This is the exact problem prompt caching (also called context caching) is designed to eliminate.

### 5.2 The KV cache, conceptually

At the level of the model's internals, what makes prompt caching possible is the key-value (KV) cache generated during the attention computation described in [Chapter 2](02-models-training-and-inference.md). As the model processes a prompt token by token, each layer's attention mechanism computes a "key" and "value" representation for every token, representations the model then reuses when attending back to earlier tokens while generating each new one. Computing these representations is the expensive part of processing a prompt.

If the same prefix of tokens appears again in a later request, byte-for-byte identical, the previously computed key and value tensors for that prefix can, in principle, be reused rather than recomputed from scratch. Prompt caching is the productized version of this idea: providers let you deliberately mark a stable prefix so that its KV representations are retained after one request and reused on the next, instead of being discarded the moment the response finishes.

### 5.3 Vendor-specific prompt caching

**Anthropic.** Claude's prompt caching lets you cache the request prefix consisting of `tools`, then `system`, then `messages`, in that order, up to a marked breakpoint (Anthropic, "Prompt caching," see References). There are two ways to enable it: automatic caching, where a single top-level `cache_control` field tells the API to cache the last eligible block and roll the breakpoint forward as the conversation grows, and explicit breakpoints, where `cache_control` is placed directly on specific content blocks for finer control.

By default the cache lives for five minutes, refreshed on every hit; a one-hour duration is available at additional cost. Anthropic prices a cache write at a premium over a normal input token (1.25x for the five-minute cache, 2x for the one-hour cache), while a cache read costs a small fraction of the standard input rate (Anthropic, "Prompt caching," see References). The cache requires an exact match: the cached prefix must be byte-for-byte identical between requests, including tool definitions, or the cache misses and the full prefix is reprocessed and re-cached, billed as a fresh write.

**OpenAI.** OpenAI's Prompt Caching works automatically, with no code changes required, for eligible prompts of 1,024 tokens or more on `gpt-4o` and newer models: requests are routed to a server that recently processed a matching prefix, and the API reports how many tokens were served from cache (`cached_tokens`) versus newly written to it (`cache_write_tokens`) in the response's usage details (OpenAI, "Prompt caching," see References).

Cache lookups are keyed on a hash of roughly the first 256 tokens of the prompt combined with an optional developer-supplied `prompt_cache_key`, which improves routing consistency for high-volume traffic sharing a common prefix. On GPT-5.6 and later models, OpenAI also supports explicit `prompt_cache_breakpoint` markers for finer-grained control, and cache writes on those models carry a 1.25x fee over the standard input rate; on earlier models, cache writes are free and only reads are discounted. What can be cached spans the full messages array, images, tool definitions, and structured-output schemas (OpenAI, "Prompt caching," see References).

A side-by-side summary of the two documented implementations:

| | Anthropic | OpenAI |
| --- | --- | --- |
| Activation | Explicit: mark a `cache_control` breakpoint | Automatic for eligible prompts, no code change required |
| Minimum cacheable length | 1,024 to 4,096 tokens, depending on model (1,024 for current Opus and Sonnet models) | 1,024 tokens |
| Default cache lifetime | 5 minutes (refreshed on each hit); 1 hour available at extra cost | 5 to 10 minutes typical, up to 1 hour, or up to 24 hours with extended retention on supported models |
| Cache write cost | 1.25x standard input (5-minute); 2x (1-hour) | No fee before GPT-5.6 models; 1.25x on GPT-5.6 and later |
| Cache read cost | Roughly 0.1x standard input | Discounted; reported via `cached_tokens` in the usage object |
| Cached content | `tools`, `system`, `messages`, in that order, up to the breakpoint | Messages, images, tool definitions, and structured-output schemas |

(Anthropic, "Prompt caching"; OpenAI, "Prompt caching," see References.)

**The shared design pattern.** Across both vendors, the practical guidance converges on the same rule: put static, reused content (system instructions, tool definitions, large reference documents) at the start of the prompt, and put variable, per-request content (the specific user question) at the end. Because caching is a prefix match, anything that changes must come after everything that is meant to be cached, or the cache breaks for that request and everything after the change point has to be reprocessed and rewritten.

**Cache invalidation.** The exact-match requirement means caching is fragile to changes you might not think of as "the prompt": Anthropic's documentation notes the cached prefix spans tool definitions as well as the system prompt and messages, so adding a tool, reordering tools, or toggling an option like extended thinking or image inputs can invalidate a cache that would otherwise still be valid, even though the visible conversation did not change (Anthropic, "Prompt caching," see References). Application code that assembles prompts dynamically needs to be deliberate about keeping the cached prefix byte-for-byte stable across calls, which in practice usually means holding tool definitions and system prompt construction fixed, and confining anything variable to the end of the request.

### 5.4 Why this makes follow-up turns cheaper

In a multi-turn conversation, every new request resends the full prior history (Section 4). Without caching, the cost and latency of processing that ever-growing history scale up with every single turn, even though most of it is byte-for-byte identical to what was just sent a moment ago. With prompt caching, the previously sent portion of the conversation is served from cache at a steep discount (roughly a tenth of the standard input price on both Anthropic and OpenAI, per the documentation cited above), and only the newest turn is processed at full price. This is precisely why caching matters more, not less, as conversations get longer: the growing shared prefix is exactly the part caching is best at reusing.

To make the mechanism concrete: suppose a system prompt plus tool definitions run 5,000 tokens, and a conversation has grown to 50,000 tokens of history, with a new 200-token user turn arriving. At standard input pricing, that turn costs the same as processing all 55,200 tokens from scratch. With a cache hit covering the 55,000 tokens of unchanged prefix at roughly a tenth of the standard rate, and only the new 200 tokens billed at full price, the effective cost of that turn drops by close to 90 percent, and because the cached tokens do not need to be reprocessed through the full forward pass, the response also starts generating noticeably faster. [Appendix C](appendices/appendix-c-costs-and-getting-value.md) works through the fuller cost arithmetic of this trade-off, including cache-write overhead and TTL (time-to-live, how long a cached entry stays valid before it expires) selection, across a complete session.

### 5.5 Semantic caching: a different concept entirely

Prompt caching (Sections 5.2 to 5.4) is an exact-match optimization: it only produces a hit when the token sequence is identical to something processed before. **Semantic caching** is a separate application-level architecture that instead matches on meaning. A semantic cache stores the vector embedding of a past query alongside its response; when a new query arrives, its embedding is compared against the cache, and if a sufficiently similar prior query is found (above a configured similarity threshold), the stored response is returned directly, without calling the model at all (AWS, "Overview of semantic caching," see References).

AWS's documentation gives a concrete illustration: "How do I install the VPN app on my laptop?", "Can you guide me through setting up the company VPN?", and "Steps to get VPN working on my computer" are three different strings that an exact-match cache (or prompt caching) would treat as entirely unrelated, but a semantic cache recognizes as the same underlying question and answers from a single cached response (AWS, "Overview of semantic caching," see References).

This makes semantic caching effective specifically for applications with high query redundancy at the meaning level even when the wording varies: RAG-based support bots and FAQ assistants, and agentic systems that repeatedly issue similar internal lookups, are the cases AWS's own documentation calls out. Reported benefits in that documentation include up to an 86 percent reduction in LLM inference cost and up to 88 percent lower latency on cache hits, though the actual gain in any given system depends heavily on how repetitive real user queries are and how the similarity threshold is tuned.

The trade-off is precision: an exact-match prompt cache can never return a wrong answer to a different question, because it only ever hits on a genuinely identical prefix. A semantic cache can, if the similarity threshold is set too loosely, return a cached answer to a query that was similar but not actually equivalent, so production semantic-caching systems need a deliberate strategy for choosing and monitoring that threshold, plus a fallback to the real model when there is no confident match. Semantic caching depends on the same embedding and vector-similarity-search infrastructure covered in [Chapter 5](05-retrieval-embeddings-and-vector-databases.md); it is, in effect, a retrieval system where the "documents" being retrieved are past question/answer pairs rather than knowledge-base content.
