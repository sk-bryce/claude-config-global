# `go-dev` 2026-09-23: v1.2.1 naming policy and project comparison

**Decision: HOLD by the thresholds as written.** The full behavioral suite scored deterministic
29/31 and judgment 7/8. Both are below the 100 percent and 90 percent gates. None of the three
failures touches content this pass changed. A one-shot re-run of the three failing cases passed two
of them cleanly and moved the third case's failure from one expectation to another (see Noise
check). That points to sampling instability on those cases, not a regression. It does not change
the recorded figure, and the gate is not waived here. Whether to release anyway is the user's call,
made at release time.

## What changed

### Part 1: naming exceptions and the returns rule

The spec changed first, then every place the rule is stated. The three copies of the naming rule
(`SKILL.md`, `go-style-preferences.md`, `go-style-conventions.md`) agree word for word.

- **Exempt:** `ok`, `err`, `t *testing.T`, `b *testing.B`, `f *testing.F`, and a short integer
  loop index declared by a `for` clause or by `for i := range`.
- **Not exempt:** range values, method receivers, and HTTP handler parameters (`writer`,
  `request`, not `w`, `r`). A one-letter receiver is graded as a failure.
- **New house rule: no named results, so no naked returns.** It binds every example in the skill,
  upstream-idiom examples included. Before this pass the only enforcement was the `nakedret` and
  `nonamedreturns` linters; no prose rule existed. The house `.golangci.yml` now sets
  `nonamedreturns` `report-error-in-defer: true`. The default exempts a named error assigned in a
  deferred function, which is the one case the rule exists to remove.
- `go-style-preferences.md`: the `Closable` example's receiver was renamed from `c` to
  `closable`. It was not showing a bug on purpose.
- `go-error-handling.md`: the deferred-Close section used a named return. It became
  `## Errors From Close on a Write Path`, which closes explicitly and returns
  `errors.Join(writeErr, closeErr)`.
- `evals.json`: cases 1, 2, 3, and 7 state the exemptions exactly. Case 1's close expectation
  forbids a named return. Case 6 gained a deterministic no-named-returns expectation. There are now
  39 expectations: 31 deterministic, 8 judgment.
- The `SKILL.md` `description:` was not touched, so no trigger re-measure was needed. The deferred
  line-break fix inside the quoted `allocation hot spot` phrase stays deferred with it.

### Part 2: two-way comparison with the user's Go service project

This half ran in two directions.

**Project into skill.** Four additions were proposed with exact text and approved one by one. All
are written in house style.

1. `go-error-handling.md`: `errors.AsType` (Go 1.26). The note says it returns the first match
   only.
2. `go-testing.md`: `## Test Contexts and Waiting Without Sleeping`. It covers `t.Context()` and
   `b.Context()`, plus a bounded `pollUntil` helper in place of `time.Sleep` waits.
3. `go-http.md`: `### Server Timeouts and Graceful Shutdown`. It sets explicit server timeouts
   (gosec G112, G114) and a zap-backed `ErrorLog`. Shutdown runs under
   `context.WithTimeout(context.WithoutCancel(ctx), shutdownTimeout)`.
4. `go-context-patterns.md`: a table of context-aware API forms that `noctx` enforces.

**Skill into project.** A findings report only, kept outside this repository. The project was not
edited. Four points were settled with the user:

- The project's own permissive declaration style governs there, per the skill's
  project-governs rule.
- `w`/`r` handler parameters are not exempt.
- `f *testing.F` is exempt.
- Named returns are banned everywhere.

The project already enforced the last point, and that fed the returns rule above.

## Verification

- **Go claims** were compiled and tested on go1.26.4, the newest local toolchain:
  - `errors.AsType` returns the first match.
  - `t.Context()` is cancelled before `Cleanup` runs.
  - `b.Context()` and `b.Loop` exist.
  - A `Shutdown` context derived from an already-cancelled parent returns `context.Canceled`
    immediately. That is why the example uses `context.WithoutCancel`.
- **Linter claims** were run with golangci-lint v2.13.2 against the house `.golangci.yml` from
  `go-style-conventions.md`:
  - `nonamedreturns` at default misses the deferred named-error case and catches it with
    `report-error-in-defer: true`.
  - `noctx` flags `net.Listen`, `net.Dial`, `exec.Command`, `db.Query`/`db.Exec`, and
    `http.NewRequest`.
  - gosec G112 fires on a missing `ReadHeaderTimeout`, and G114 on `http.ListenAndServe`.
- **Linting the new examples:** the inserted blocks lint clean apart from gosec G304 on
  `os.Create(path)`, the same class the replaced example carried, and scaffolding-only `goimports`
  notes. `golangci-lint config verify` passes on the edited config.
- **Parse check:** the total is still exactly 3 unparseable blocks (go-concurrency blk_6, go-http
  blk_12, go-style-conventions blk_6). go-http now has 13 blocks and go-testing 5.
- **Framing note:** byte-identical in all eight reference files that carry it.
- **Other gates:**
  - `SKILL.md` frontmatter loads with `yaml.safe_load`.
  - Both eval files load.
  - No non-ASCII was added.
- **md-checks** exits 0. It reports one known false positive: the `errors.AsType` call inside a
  fenced block in `go-error-handling.md` reads as a link (type argument in brackets, then the call's
  argument in parentheses), because link checks run inside fences.
  The script's header documents that as intended. The prose instance was reworded to avoid it.

## Noise check: cases 3, 4, 6 re-run once

Case 4 swapped one failure for another. This time the executor chose a collect-all reading of the
prompt and deliberately left out cancel-on-failure, and documented how to add it back. The first
build recorded the same deviation, which is why `go-concurrency.md` gained its collect-all-plus-cancel
section. The first build's eval critique already flagged this expectation. It demands both
collect-all and stop-on-failure, which are in tension in the prompt as written. That tension has not
been fixed.

## Observations outside the graded expectations

- **Case 8** called a reassignment "shadowing". It also used a separate `groupCtx` rather than
  reassigning `ctx`, contrary to the guidance in `go-style-preferences.md`. The graded expectations
  did not cover either point.
- **Case 4, iteration 2:** the executor wrote `:=` in a short usage snippet while
  the main code conformed. The house rule does not exempt snippets, and the judgment grade counts
  them.
- **Go 1.27:** the compared project already declares `go 1.27`. The skill's claims were verified on
  go1.26.4. By the spec's re-check trigger, a Go minor release newer than the skill's `updated:`
  date is a staleness signal for the whole skill.

## Open

1. **Case 4's expectation still needs splitting or rewording.** First flagged by the first build.
   The prompt asks to "collect errors" and the expectation also demands stop-on-first-failure.
2. **Case 6's `%w` expectation assumes a sentinel** the prompt does not ask for. Either the prompt
   should name an underlying error, or the expectation should accept a sentinel-free error when
   there is nothing to wrap.
3. **Case 3 and case 6 pass on re-run.** More runs per case would separate instability from a
   real miss. The suite currently runs each case once.
4. **Re-verify the skill's version-dated claims on Go 1.27** once that toolchain is available
   locally.
