# 1. Adopt a spec-anchored, spec-driven architecture for this config

- Status: Accepted
- Date: 2026-07-26
- Deciders: repository owner

## Context

This repository configures the Claude Code agent harness from one `~/.claude` tree.
The obvious mechanism is a single build document intended to generate, regenerate, and
improve every artifact (skills, hooks, subagents, global rules) as harnesses and models
change over time, while also serving as the record of intent behind those artifacts.
The generated artifacts are committed to git.

Evaluated against how it actually behaves, that mechanism has concrete, observed
problems, not hypothetical ones:

- The single document grows without bound - past 780 lines - and mixes three document
  types that have different natural lifetimes: imperative build instructions, a dated
  decision log, and a to-be-determined backlog.
- It duplicates content that already lives in the artifacts it produces. Its Skills
  section restates the working `skill-author` skill, and it embeds a full copy of
  `CLAUDE.md` content that drifts from the live file.
- The regeneration unit of work is the whole file, which is expensive enough that a
  full pass gets deferred, leaving designed-but-unbuilt sections stale.

The requirement that matters most, per the owner, is that intent, behaviors, and
desired artifacts survive periodic "regeneration cycles" when a new harness or model
version warrants rewriting an artifact.

Research into current practice (2026) shows this is a solved category. Spec-Driven
Development (SDD) treats a versioned specification, not the artifact, as the durable
carrier of intent, and Birgitta Boeckeler's taxonomy names three rungs: spec-first,
spec-anchored, and spec-as-source. Because our generator is a non-deterministic LLM,
the industry rule for committing generated output (commit it when regeneration is
slow, external, or non-deterministic, and never hand-edit it without updating the
source) applies, which places us on the spec-anchored rung and rules out spec-as-source
(named an anti-pattern that inherits "the downsides of both MDD and LLMs: inflexibility
and non-determinism").

## Decision

Adopt a spec-anchored architecture with four separated layers, in place of any single
build document.

1. Constitution / steering (persistent, runtime-loaded governing principles):
   `CLAUDE.md` plus `reference/*.md`. These are hand-maintained source, referenced
   by everything else, never duplicated into it.
2. Specs (per-artifact intent, the regeneration source): a new `specs/` tree, one
   file per artifact type with a section per artifact (for example `specs/skills.md`,
   `specs/behaviors.md`). Specs hold purpose, behavior, non-goals, trigger phrases,
   constraints, and testable acceptance criteria only. They never copy artifact
   content and never contain imperative "how to generate" procedures.
3. Generated artifacts (committed, treated as regenerable): `skills/`, `agents/`, and
   the mechanical outputs. These stay committed because LLM regeneration is not
   reproducible, so the committed artifact is the record of what is actually loaded.
4. Decisions (immutable history): a numbered `decisions/` directory of ADRs.

Supporting rules:

- Artifacts are split into two classes. Mechanical artifacts (for example the
  `references/` copies a skill loads, kept in step with their source documents) are
  deterministic and produced by `scripts/sync.sh`. LLM-generated artifacts (skills, subagents) are regenerated by their authoring skill
  from the spec and gated by evals.
- The regeneration mechanism is the per-artifact-type authoring skill (`skill-author`
  today), invoked in scoped, per-artifact fashion, not a wholesale re-run of one file.
- A regeneration is gated by evals using the existing native skill-creator/skill-author
  eval framework first, with paired comparison against the committed prior version.
- Every generated artifact carries a provenance header (source spec, agent, model,
  and harness version at generation time).
- Scripts and hook logic may be model-generated and reviewed before commit; hook registration
  (the entry that activates a hook) requires the user's explicit, in-the-moment direction.
  See ADR 3.

## Consequences

Positive:

- Intent is durable and greppable, co-located by type but outside the disposable
  artifact directories, so a skill directory can be deleted and regenerated.
- Regeneration is scoped to one artifact, cheap enough to actually happen when a
  harness fact changes.
- No duplicated content, so the `CLAUDE.md`-versus-copy drift class disappears.
- Non-deterministic rewrites are made safe by an eval gate and a reviewable diff
  against the committed prior version.

Negative or residual:

- LLM regeneration remains non-deterministic; evals bound behavior, not wording.
- The "big ball of specs" risk is real; the no-copied-content and no-procedures rules
  are conventions that must be held, not guarantees the structure enforces.
- There is no calendar forcing function; regeneration is event-triggered (a
  `skills/cursor-projection/references/harness-matrix.md` change or an eval regression).

## Alternatives considered

- Keep a single build document, with fixes (evals, hooks carve-out, spec/record split).
  Rejected: does not address unbounded growth, content duplication, or the wholesale
  regeneration unit.
- A self-pruning build document that shrinks as categories graduate. Rejected: still a
  standing file holding three document types in tension, and still requires pruning
  discipline.
- Pure static content plus sync scripts plus a simple intent doc. Close, and largely
  adopted here, but underspecified for genuinely new artifact categories and for how
  intent survives a rewrite; the spec-anchored framing supplies that.
- Spec-as-source (spec is the only maintained artifact). Rejected as an anti-pattern
  for a non-deterministic generator.
